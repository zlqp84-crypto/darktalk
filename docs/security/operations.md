- Git은 코드 이력이며 DB/Auth/Storage 데이터 백업을 대신하지 않는다. 원천 기업 자료 역시 사용자 데이터 백업이 아니다.

## 현재 제공하는 검사

- `security-checks.example.yml`: main push와 PR에서 설치·lint·격리 DB 권한 테스트를 실행하는 준비 파일. 현재 Git 토큰에 workflow 권한이 없어 GitHub가 workflow 파일 푸시를 거부했다. 따라서 `.github/workflows`에는 활성화하지 않았고 CI 실행은 미완료다. 권한을 갖춘 정상 경로로 등록 후 실행 성공 여부를 확인해야 한다. 이메일 수신 여부는 GitHub 계정 알림 설정에 달려 있다.
- `scripts/verify-p1-public.mjs`: 설정된 운영 공개 키로 익명 접근 차단과 비로그인 읽기를 검사한다. 원문·토큰·ID를 출력하지 않는다. 주기 실행은 설정하지 않았다.
- `instrumentation.ts`: 서버 요청 오류의 고정 이벤트 코드와 종류만 기록한다. 예외 메시지·스택·헤더·요청 경로를 추가 전송하지 않는다. 외부 오류 수집 서비스나 알림 채널은 연결하지 않았다.

## 백업·복구 도입 순서

1. 사용자 선택: 별도 암호화 백업 저장소를 마련해 직접 백업하거나 Supabase의 백업 제공 플랜을 사용한다. 비용 발생 조치는 별도 승인 대상이다.
2. 안전한 로컬 입력으로 DB 연결 정보를 설정한다. 비밀번호를 채팅/명령 인자/Git/로그에 넣지 않는다.
3. DB 스키마·데이터·역할을 적절히 덤프하고 Storage 파일은 별도로 백업한다. DB 덤프에 파일 본문이 포함된다고 가정하지 않는다.
4. 운영과 분리된 복구 환경에 복원하고 사용자/콘텐츠/파일 수, 외래키, RLS, 관리자 MFA, 익명 응답을 검증한다.
5. 성공한 백업의 보관 기간·암호화·접근자·실패 알림을 정한 뒤 정기화한다.

백업 생성 및 복구 리허설을 완료했다고 표시하지 않는다. 운영 DB를 복구 테스트 대상으로 사용하지 않는다.

## Migration 이력

CLI db push를 먼저 실행하지 않는다. 운영 스키마/함수/정책/트리거를 덤프하여 저장소 migration 적용 결과와 대조하고, 실제 반영된 버전만 이력에 등록한다. 명칭이나 파일 존재만 보고 전체 버전을 적용 완료로 표시하지 않는다.

## 탈퇴 실제 삭제 실행기

현재 구현은 접수·상태 조회·처리 전 취소이다. 실제 계정 삭제는 완료되지 않았다.

- 삭제 범위(콘텐츠 동시 삭제 또는 계정 연결 해제)를 확정하고 사용자 안내와 일치시킨다.
- 재인증 및 명시적인 본인 확인 후 처리 상태를 잠그고 중복 요청을 멱등 처리한다.
- Storage API로 확인된 본인 소유 객체를 삭제하고 결과를 검증한다. storage.objects 메타데이터를 SQL로 직접 삭제하지 않는다.
- DB 콘텐츠·참조를 정리한 뒤 Auth Admin API로 계정을 삭제한다. 관리자 계정은 별도 권한 이전이 필요하다.
- 단계별 실패 시 재개할 수 있어야 하며, 모든 단계가 성공하기 전에는 탈퇴 완료로 표시하지 않는다.
- 삭제 실행용 서버 키는 브라우저 번들에 포함하지 않는다. 현재 접수 RPC에는 임의 사용자 삭제 기능이 없다.

## 데이터 갱신

아직 정기 갱신/병합을 실행하지 않았다. 기존 원천 수집기를 갱신용 upsert와 검토용 차이 보고로 확장해야 한다. 이름 일치만으로 병합하거나 원천에서 빠진 항목을 폐업으로 처리하지 않는다. 기존 회사 ID·slug·리뷰 연결 및 수동 공개 상태를 보존한다. 행정기관 자료는 공식 식별자·이용 조건 확인 후 별도로 등록한다.

후속 상태(2026-09-28): HIRA 주간 갱신을 로컬 Codex 예약 `darktalk`로 활성화했다(매주 월요일 10시, 한국시간). 공식 세부정보가 일치하는 중복 5쌍의 대표 연결을 운영에 적용했다. 정기 예약의 미래 실행 성공, 미확정 3쌍 통합, 타 출처 정기화는 완료되지 않았다. 현재 절차는 `docs/hospital-recurring-runbook.md`, 통합 근거·정책은 `docs/company-merges.md`를 따른다.

### 병원 갱신 사전 비교 도구

`scripts/companies/compare-hospitals.mjs`는 기존 수집기의 완전한 JSON 스냅샷 두 개를 비교한다. 동일한 출처 식별자로만 대조하여 추가·명칭/분류/지역 변경·목록 누락·변경 없음을 분리한다. 누락은 폐업 판정이 아니며 DB 변경이나 SQL 생성은 하지 않는다. 불완전한 목록, 중복 식별자, 이전 날짜 입력은 거절하고 기존 보고서 파일을 덮어쓰지 않는다.

```powershell
node scripts/companies/compare-hospitals.mjs --before artifacts/companies/hira-OLD.json --after artifacts/companies/hira-NEW.json --output artifacts/companies/hira-review-NEW.json
```

초기 검증에서는 저장된 2026-09-21 자료 79,858건의 자기 비교를 완료했다. 이후 2026-09-27 최신 자료 79,874건을 수집하고 `prepare-hospital-refresh.mjs`를 통한 검토·롤백 검사 후 운영에 반영했다. 신규 28건 공개, 중복 후보 8건 비공개, 기존 9건 변경, 누락 20건 유지. 자세한 적용 증거와 다음 실행 절차는 `docs/company-expansion.md` 참조. 전체 테스트 258개 통과. 정기 실행 및 자동 병합은 미연결이다.
